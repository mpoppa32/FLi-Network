### 2026-08-05 — Reviewer subagent caught three real bugs in the CI diff pre-push   [LANDED / LESSON]
First run of the new `.claude/agents/reviewer.md`, against its own author's staged diff. Three findings that would each have shipped a green-but-wrong pipeline:
1. **Silently-skipped deploy.** Deploy target was computed with `git diff HEAD^ HEAD` — only the LAST commit — while GitHub's `paths:` filter spans the whole push. Also caught: the truth-doc section stated never-executed behavior in the present indicative (Rule 2), and cited `index.ts` as naming files it does not name.

(c) never end a guard function in a pipeline — the subshell eats its exit status. (d) run the reviewer BEFORE the first push, not after; all three were free to fix at that point.

### 2026-08-05 — CT-1b acceptance FAILED: telemetry persist uses the exact SDK call P13.354 exists to avoid   [FAILED / REAL BUG]

### 2026-08-06 — Meeting PROCESS hangs forever on a wedged socket: `fbSet`'s own fallback is the trap   [OPEN — Mission 4 #4]
Reproduced twice by the operator: PROCESS → "Analyzing" indefinitely, no error, no console output, and a network capture armed before attempt 2 shows **zero requests to `anthropicProxy`**. RTDB `.lp` channel returning **503** throughout.
**Diagnosis CORRECTED against source — it is not a read.** The handoff said the flow dies on SDK *reads* before the fetch. It dies on an SDK **write**, in `fbSet` itself (`FLiIntel.html:12687-12692`), and fixing reads would not have fixed it:
1. `12689` fires `set()` fire-and-forget with `.catch(function(){})`. On a wedged socket this promise **never settles**.
2. `12690` is the P13.354 REST `PUT`, but it returns early **only on `_r.ok`**. With RTDB 503, `_r.ok` is false, so it falls through instead of failing.
3. `12691` then does `await (_p||set(...))` — awaiting **the hung promise from step 1**. It never resolves and never rejects.
Everything downstream follows from that one await: `saveMeeting` (`13080`) never resolves → `await saveMeeting(m)` in the process path (`26431`) never resolves → the `try/catch` at `26430-26436` cannot fire because there is no rejection → `_processMeetingAI` (`26469`) is never reached → `callClaude` is never reached → **no request to `anthropicProxy`, no error, no console output, button stuck on "Analyzing."** Every reported symptom is explained by line 12691.
**The structural lesson, and it is the sharp one:** P13.354's fallback treats "REST returned non-ok" as "REST unavailable, fall back to the SDK." Under a wedge those two conditions **co-occur** — same broken network — so the fallback hands control to the hung path in precisely the situation it was written to survive. The safety net is wired to the thing it was catching.

### 2026-08-25 — A hazard test that could only ever pass where it was written   [FIXED]
The two `Date.parse` hazard tests — the ones pinning `"Phase 1"` → `2001-01-01`, the regression the whole `actionItemArchive` module exists for — went **red on this machine against code nobody had touched.** Not a data change and not a bad merge: the machine's timezone had moved to `Asia/Singapore`.
`Date.parse` on free text resolves to **LOCAL** midnight. The assertions read that instant back with `toISOString()`, i.e. in UTC. The tests passed in CI (UTC) and on a US-timezone laptop and were **structurally incapable of passing in half the world** — a latent red that CI can never catch, because CI is the zone they were written in.
FIX: compare on local calendar fields (`getFullYear`/`getMonth`/`getDate` via a `ymdLocal` helper), then re-run green under `Asia/Singapore`, `UTC` and `America/New_York` — three zones spanning UTC+8 to UTC−5, rather than declaring it fixed from one run.
Worth stating: the local-midnight behaviour is *part of the hazard*. A test pinning `Date.parse`'s misbehaviour that then reads the result through a different clock is measuring two things and attributing the answer to one.
DO NOT REPEAT: **a test that pins a hazard must not itself depend on where it runs.** Any assertion mixing `Date.parse` (local) with `toISOString()` (UTC) is timezone-dependent by construction. ### 2026-08-25 — "Leave the array empty" was not representable; probed rather than assumed   [SPEC CORRECTED]
Relay 023 specified that Anduril's `meetings` array should go to zero entries and "leave it empty, do not delete the field." **RTDB cannot store an empty array.** Probed in the TEST workspace before building on it: writing `{arr: []}` over `{arr:[1,2], keep:"x"}` returns `{"keep":"x"}` — the key is gone, the sibling untouched. So the field will be ABSENT, not empty.
It makes no behavioural difference here — every consumer in this codebase reads `Array.isArray(n.meetings) ? n.meetings : []`, so absent and empty are the same value to all of them — but the spec asked for something the datastore cannot do, and the difference is now asserted in the verify step instead of quietly delivered as "close enough".
DO NOT REPEAT: Rule 14 again, on a datastore rather than on code. "Leave it empty" is a claim about what the storage layer can represent, and empty containers are exactly where RTDB's semantics differ from JSON's. **Probe the write in the TEST workspace before promising a shape** — it cost one throwaway probe and it turned an unnoticed silent difference into a stated one.

## INTEGRITY TIER (CT-1 … CT-4)
`recordPipelineEvent` (P13.392/CT-1) is the single choke point for pipeline telemetry: in-memory + `localStorage` ring buffer (100 entries), console on `sync_error`/`invariant_warn`/`persist_error`, toast on the first two. - **CT-1b persistence (2026-08-05): BUILT, DEPLOYED, and ACCEPTANCE FAILED — DO NOT TREAT AS WORKING.** `recordPipelineEvent` is *intended* to ALSO write each event to `workspaces/{wsId}/pipelineHealth/{ph-<ms>-<rand>}` so health survives a reload and is readable server-side. Written with a direct `ref`+`set` (`FLiIntel.html:27732`), fire-and-forget so telemetry can never block the pipeline — **deliberately NOT through `fbSet`**, because CT-4 instruments `fbSet` failures *by calling `recordPipelineEvent`*, so routing through `fbSet` would re-enter the recorder on every failed write.   - **Measured 2026-08-05 (Mike's signed-in browser, Atlas, connection header showing DELAYED):** two `recordPipelineEvent('selftest', …)` calls both landed in the local buffer, **neither reached `pipelineHealth`, and NOTHING was printed to console.** Ruled out by that session: duplicate definitions, scope resolution, stale `currentWsId` (`wsPath` probe correct), and the database rules (a direct REST `PUT` returned 200 and its probe record is in `pipelineHealth`).
  - **Why the design is wrong:** the raw SDK `set()` on line 27732 is the exact call `fbSet` was rewritten to stop using. `FLiIntel.html:12688` (P13.354) records that on this operator's network the realtime socket wedges and the SDK `set()` server-ack **hangs forever** — so `fbSet` fires the SDK write non-blocking and persists durably via a REST `PUT` with the user's id token. CT-1b has no such fallback, and a hung promise **never rejects**, so its `.catch` (27733) and its `try/catch` (27737) can never run. That is precisely why there was no console output: the code cannot report this failure mode by construction.
  - **Second defect, same symptom:** the guard on 27730 fails **silently** — no `console`, no marker. So a skipped write and a wedged write are indistinguishable from the browser, which is a Rule 11 violation inside the instrumentation whose whole job is to make silent failure impossible. Strictly, the evidence to date cannot separate "socket wedge" from "guard was false"; the DELAYED header points hard at the wedge, and the fix must close both.
  - **Net effect: CT-1b drops health events exactly when they matter most — during network trouble, which is the condition it exists to record.** The local ring buffer still holds them, so nothing is lost while the tab lives; the durability claim is what fails. Prior claim in this doc — that a failed persist is `console.warn`'d and therefore not silent — was **wrong as written** and is corrected here.

## WRITE LAYER — P13.398 (2026-08-06), wedge-proofed for real

**FIXED, harness-verified; live acceptance owed.** `fbSet`/`fbRemove` previously hung forever on a wedged socket: the SDK promise was fired fire-and-forget, the REST path returned early **only on `_r.ok`** (so an RTDB 503 fell through), and the last line then `await`ed that same never-settling promise. A hang never rejects, so nothing reported it — **meeting PROCESS stalled at "Analyzing" with no error, no console output and zero requests to `anthropicProxy`**, because `saveMeeting` → `fbSet` is the first `await` in the process path. Reproduced twice 2026-08-06. CT-4's `persist_error` was blind to it too (it sits in a `catch`).

- **The structural fix:** REST is now **authoritative**, not a preferred-but-optional path. A non-ok response is a failure to surface, never a reason to fall back — the old logic treated "REST 503" as "REST unavailable, use the SDK", but under a wedge those conditions **co-occur on one broken network**, so the safety net handed control to the hung path in exactly the case it existed for. The SDK write remains optimistic (instant local update + `onValue`) but is **raced against `FB_WEDGE_MS` (8s), never awaited unbounded** — a hang is detectable only by clock, never by `.catch` (the CT-1b/P13.397 lesson). `getIdToken()` is itself a network call and is timed out too; the REST `fetch` carries an `AbortController` deadline.
- **Rule 11 surfacing on failure:** `setSS('error')` + `console.error` naming *both* paths + a `persist_error` health event + an operator toast, then a **throw** — so callers like the process path's `try/catch` (`26430-26436`) finally fire instead of waiting forever. Wording is deliberately "could not confirm write", not "write failed": a timed-out SDK write may still land later.
- **Verification: `scripts/fbwrite-harness.mjs` — 18/18 green.** Extracts the shipped `fbSet`/`fbRemove` by marker and drives them against stubs reproducing the observed combination (REST 503 + never-settling SDK promise), plus hung `getIdToken`, missing user, REST rejection, and the happy path. **Proven non-vacuous:** the pre-fix implementation under those same conditions **HANGS** — outcome `HUNG`, sync state stuck on `saving`, **zero** console errors and **zero** health events, reproducing the observed symptom exactly.

## CI/CD + GOVERNANCE MACHINERY (2026-08-05)

**STATUS: LIVE + VERIFIED 2026-08-05.** Observed green end-to-end on run [#3](https://github.com/mpoppa32/FLi-Network/actions/runs/30993064184) (commit `50257ad`): a comment-only change to `functions/src/index.ts` pushed to `main` deployed itself with no human action — **77 × `Successful update operation`**, including `operatorData`, and including the gitignored private functions `atlasMasterSync` / `triggerAtlasMasterRead` / `triggerAtlasMasterSync`, which proves the bundle-restore path works and that nothing was pruned. Deploy 6m27s, post-deploy smoke green, `verify-live` green.

- **Prerequisite that bit us once:** the **Cloud Billing API** must stay enabled on project `fli-network`. It was disabled at first run; `firebase-tools` reads `cloudbilling.googleapis.com/v1/projects/fli-network/billingInfo` as a preflight (gen2 functions require Blaze) and the deploy aborted 403 *before touching any function*. Enabled 2026-08-05; deploys green since. See LOG.

- **`.github/workflows/firebase-deploy.yml`** — a push to `main` touching `functions/**`, `database.rules.json`, or `firebase.json` builds and deploys. Auth via the `FIREBASE_SERVICE_ACCOUNT` GitHub secret (`google-github-actions/auth@v2` → ADC → firebase-tools). `firebase-tools` pinned to `15.17.0`. `--non-interactive` **without** `--force` is deliberate — if the private config fails to restore, the CLI aborts instead of pruning four live production functions.
  - Deploy target is computed in a separate `changes` job from **`github.event.before`…`github.sha`** with `fetch-depth: 0, filter: blob:none` — deliberately NOT `git diff HEAD^ HEAD`. `HEAD^` sees only the last commit while GitHub's `paths:` filter spans the whole push, so a push of *[commit A: rules, commit B: functions]* would deploy functions and **silently skip the rules change on a green run** — reintroducing the exact failure class this workflow exists to kill, on the security-critical surface. An unresolvable range (force-push, first push) falls back to deploying both.
  - Push `paths:` includes the **front end** (`FLiIntel.html`, `FLiIntel.css`, `js/corsair/**`) as well as the backend. This is load-bearing, not decorative: with backend-only paths, `verify-live`'s byte assertion could never fire on a front-end-only push and would pass trivially on every backend push, because `FLiIntel.html` would be unchanged. Backend-only paths made the whole check vacuous.
  - Also runs on `pull_request` (build only — every deploy step gated `if: github.event_name == 'push'`), so a broken branch shows a red X without reaching `main`. Fork PRs are skipped rather than run: they receive no secrets, so they could not compile and would go red for reasons unrelated to the code.
  - Post-deploy smoke: asserts `operatorData` returns **401** to an invalid bearer token. `firebase deploy` can report success while a function is stuck on an old revision or failed to bind a secret; without this, nothing verified the surface the workflow actually deploys.
  - `npm test` runs in its own step **between build and every deploy step**, on push and PR alike (Mission 3, 2026-08-05). See the TEST SUITE section below. This closes the gap this doc previously recorded ("zero test files; `vitest run` exits 1; not wired in").
  - `verify-live` asserts **`sha256(live FLiIntel.html) == sha256(repo FLiIntel.html)`** (12 attempts, 25s apart, no-cache headers). That single assertion is what closes the LOG 2026-08-02 failure class. A *hardcoded* marker list cannot: markers are additive and permanent, so such a check can only ever pass. Marker comparison is therefore demoted to a failure-only diagnostic and its set is **derived from the repo at runtime** (195 unique `P13.x` markers today), to turn a hash mismatch into a named diff.

- **The public-repo build constraint (important, previously only an `index.ts` comment).** `functions/src/index.ts` exports four functions (`triggerAtlasMasterRead`, `triggerAtlasMasterSync`, `atlasMasterSync`, plus `factsSync`/`draftingFacts`/`slack/config` imports) whose source is **gitignored** — private Sheet IDs and customer names, and this repo is PUBLIC. **A clean checkout does not compile.** Measured 2026-08-05 on `git archive HEAD`: `tsc` fails with 14 errors, 8 of them `TS2307: Cannot find module '../sources/atlasMaster/…'`.
  - CI restores the 7 private files from the `ATLAS_MASTER_BUNDLE` GitHub secret (base64 tar.gz, 13,277 chars; GitHub's limit is 48 KB), produced by `scripts/atlas-bundle.sh bundle`.
  - **`functions/atlasMaster.sha256`** is a committed, non-sensitive sentinel: filenames plus SHA-256 digests. Non-sensitive because every one of those basenames already appears in tracked public files — `functions/src/index.ts:68-72` names the three top-level modules, and `factsSync/mapper.ts:32-33`, `http/draftingFacts.ts:20`, `jobs/factsSheetSync.ts:14`, `sources/slack/config.ts:12` name the `sources/atlasMaster/*` ones — and a SHA-256 of a multi-KB source file is not invertible. CI verifies the restored bundle against it and fails loudly on mismatch, closing the drift hole where an edited private file leaves the secret silently stale and CI deploys old config forever. Both must be refreshed together (`scripts/atlas-bundle.sh sentinel` + `bundle`); the pre-commit hook warns when they diverge.

- **`.githooks/pre-commit`** — committed git hook. Guard 1: a commit touching `FLiIntel.html` or `functions/**` without staging `corsair-ops-truth-v1.md` (Rule 6). Guard 2: private-config sentinel drift. Mode via `git config corsair.truthlock warn|block`, **default `warn`**. Chosen over a Claude Code hook because it fires on every commit — Mike's, Bryce's, any agent's — not only on commits made through an agent harness. **Requires per-clone activation: `git config core.hooksPath .githooks`** — an unactivated hook is an inert file, so treat that command as part of cloning this repo.

- **`.claude/commands/{ship,truth-check,postmortem}.md`** and **`.claude/agents/reviewer.md`** — the four-doc rituals as slash commands plus an adversarial diff-review subagent. The reviewer earned its place immediately: run against this very diff before its first push, it found a silently-skipped-deploy bug, a vacuous live check, and a swallowed-failure bug in `atlas-bundle.sh`. ## STALENESS — FOUR COEXISTING NOTIONS (2026-08-11)

Full audit in **`corsair-staleness-inventory-v1.md`** (read-only, every rule cited to file:line). The short version, because "stale" was being used to mean four different things:

| Notion | Entity | Rule | Where | Writes? |
|---|---|---|---|---|
| `isStale(item, now)` | commitment | `open` && `created` >30d && (undated \|\| overdue >7d) | `jobs/commitmentsAutoArchive.ts:50-88` | **yes** (nightly 04:30 UTC) |
| `stale` column | opportunity | active stage && no linked meeting ≥14d | `js/corsair/brief.js:261-335` | no |
| `aged` column | opportunity | `daysInStage > stage ageLimit` | `js/corsair/pipeline.js:155-165` + `brief.js:647-687` | no |
| `decay` column | person | no contact ≥30d | `js/corsair/brief.js:194-258` | no |

The `stale=15` / `aged=330` numbers in the brief's console telemetry (`brief.js:794`) are the two **opportunity** metrics — not commitments and not action items. **Meeting action items have no staleness rule at all**, and that is the only real gap.

- **Measured on live Atlas 2026-08-11 (>21d overdue, `deadline` falling back to `due`):** commitments **0** of 51 open (all ISO-dated, overdue range +5d…−35d); action items **43** of 359, across 7 meetings, 28 high / 15 medium, 42-105 days overdue.
- **`due` does not exist on a single record** in either path — the union of commitment keys and of action-item keys both carry `deadline` only. This independently re-confirms that the three front-end filters gating on `c.due` are inert on real data.
- **Action items have NO completion field.** All 359 carry exactly `context, deadline, owner, priority, task` — no `done`, no `status`. So `isOpenActionItem()`'s `done` test, correct as written, currently excludes nothing: **every action item is permanently "open" and the operator has never had a way to mark one finished.** The 43 are not provably abandoned. Additive `done` / `archivedAt` / `archivedNote` fields are the queued fix and must land before any sweep.
- **79% of action-item deadlines are free text** — 74 ISO-dated, 282 free text (`"Ongoing"`, `"TBD"`, `"Phase 1"`, `"Upon contract signing"`), 3 empty. Every date filter in the app is blind to those 282. **`Date.parse()` does not reject them, it invents dates:** an unguarded first pass reported `"Phase 1"` as **9,352 days overdue** (V8 resolves it to year 0001). Any date logic on this field must require a strict ISO prefix and treat everything else as undated.
